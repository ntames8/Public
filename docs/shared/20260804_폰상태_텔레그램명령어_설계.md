# 폰 상태(화면/배터리) 텔레그램 명령어 — honeybot 이관 설계

- 작성일: 2026-08-04
- 작성 세션: stockmonitor (읽기 전용 조사 + `screen_watchdog.py` 프로토타입 구현)
- 실제 구현 대상 세션: honeycard/honeybot
- 상태: 설계 초안, 미착수

## 1. 배경 — 조사 흐름

stockmonitor 세션에서 아래 순서로 진행되며 나온 결과물이다. 각 단계가 다음 단계의
필요성을 낳은 흐름이라 순서대로 남긴다.

### 1.1 폰 화면 점검 요청

"켜져있지 않은지, 켜진 채로 프로그램을 끝내진 않았는지" 확인해달라는 요청으로 시작.
phone #1/#2의 화면 상태를 점검하다가 phone #1이 배터리 0%로 완전 방전된 상태를 발견.

### 1.2 배터리 방전 원인 추적

phone #1이 오프라인·충전 중이라 실기기 조작 없이 `collector.log`만으로 역추적.
08-03 08:45~15:30까지는 수집이 정상 동작했으나, 15:32부터
`RuntimeError: 네이버페이 버튼을 찾을 수 없습니다` (`naver_parser.py:351`,
`_naver_restart`)로 반복 실패 시작. 동시에 로그의 "화면 상태 저장/복원" 라인을 보면
08:45~15:30 전 구간에서 저장되는 **기준값 자체가 `stay_on=3`(충전 중 항상 켜짐)** 으로
고착되어 있었음 — 즉 이 문제가 08-03 하루의 일이 아니라 그 이전부터 매 수집 사이클마다
"고장난 상태를 정상으로 착각하고 그대로 복원"하는 식으로 스스로 유지되고 있었다는 뜻.

### 1.3 crontab 간섭 가설 검증

phone #1에서 동시에 도는 3개 서비스(`monitor_phone.sh`→xwiki 기동,
honeycard/`start_honeybot.sh`, stockmonitor/`start_server.sh`)가 서로 간섭했을
가능성을 crontab 목록과 각 스크립트로 추적. `monitor_phone.sh`(10분마다 인터넷 연결
확인)가 실패 시 `run_xwiki.sh`를 기동하는데, 이 스크립트가 `adb kill-server`
(연결된 **모든** 기기의 adb 세션을 통째로 끊는 전역 명령)를 쓰고 있었고, 실행 전에
`/sdcard/device.lock`(stockmonitor/honeybot이 공유하는 "지금 작업 중" 표시 파일)을
전혀 확인하지 않는 것을 확인. 이게 stockmonitor 수집 중(화면 30분 타임아웃 +
`keep_screen_on()`으로 항상 켜짐 설정한 상태)에 끼어들면, 세션이 끊기면서
`finally` 블록의 `restore_screen_state()`가 실행되지 못하고 화면 보호 설정이
고착되는 인과관계가 성립함 — 1.2에서 본 증상과 정확히 들어맞음.

(lock 대기 로직을 `run_xwiki.sh`에 추가하는 방안도 검토했으나, "인터넷 장애처럼
긴급도 높은 복구 작업이 이미 실패 중일 lock 보유자를 기다려줄 이유는 없다"는
판단으로 폐기하고 아래 3.2 방식으로 선회.)

### 1.4 `run_xwiki.sh` 수정 및 실기기 검증

`adb kill-server` → `adb -s $TARGET_DEVICE reconnect`로 범위를 phone #1로 한정
(phone #2 등 무관한 기기 세션 보호), 스크립트 끝에서 화면 보호 설정
(`screen_off_timeout`, `stay_on_while_plugged_in`, `screen_off_pocket`)을 기본값으로
무조건 되돌리는 방어 로직을 추가 — stockmonitor의 자체 복원 로직이 못 돌더라도
안전망 역할. phone #1 재연결 후 직접 실행해서 phone #2 세션이 끊기지 않고 유지되는 것,
설정값이 의도대로 복원되는 것까지 실기기로 검증 완료.

### 1.5 화면/배터리 상시 감시 필요성 대두 → `screen_watchdog.py`

"화면이 계속 켜져있는 게 정상인지 비정상인지 그때그때 구분이 안 된다"는 문제 제기로,
phone #1/#2를 10분 간격으로 감시하는 별도 프로그램을 프로토타입으로 작성.
화면 상태(`dumpsys power`)와 `/sdcard/device.lock` 유무, 배터리 레벨/충전 여부
(`dumpsys battery`)를 읽어서:
- 화면이 정당한 이유(lock) 없이 켜진 채로 2회(~20분) 지속
- 충전 중인데 배터리가 2회(~20분) 연속 하락

위 두 조건 중 하나가 발생하면 텔레그램으로 1회성 알림을 보내는 구조로 구현.
기존 honeybot 텔레그램 봇(`**********:****` 토큰, `**********` chat_id)에 알림을
얹어 보내는 방식으로 만들었고, cron 등록(`*/10 * * * *`) 후 실제 실행 로그로 스케줄
정상 동작을 확인했으며, 배터리 하락 시나리오를 시뮬레이션해 실제 텔레그램 알림
발송까지 end-to-end로 검증 완료.

이 스크립트는 stockmonitor 리포 바깥(`~/screen_watchdog.py`)에 독립 파일로 존재하고,
cron에도 별도 등록되어 있다. **책임 소재상 이 기능은 stockmonitor보다 honeybot에 속한다**
— stockmonitor는 phone #1의 주식 데이터 수집기이고, "폰 상태를 텔레그램으로 조회/감시"는
honeybot이 이미 담당하는 영역(카드 알림, `/screen` 명령어로 phone #1 화면 제어)과 정확히
겹친다. 이 이관이 이번 문서(2절 이하)의 본론이다.

### 1.6 알림 발생 조건 (현재 동작 방식)

- **주기**: cron이 10분마다 실행 (`*/10 * * * *`). 매 실행마다 텔레그램을 보내는 게
  아니라, 아래 조건을 판정만 하고 로그에 남긴다.
- **트리거**: 화면·배터리 두 조건(1.5) 중 하나가 **연속 2회(≈20분) 지속**될 때만 발송.
  1회 튐(fluctuation)으로는 안 감 — 연속성 요구가 노이즈 필터 역할.
- **1회성(one-shot)**: 조건 충족 시 딱 1번만 보내고, 문제가 해소될 때까지 재발송 안 함
  (스팸 방지). 정상으로 돌아오면 카운터/알림플래그가 리셋되어, 이후 재발생 시 다시 알림.
- **정상 상태는 침묵**: 조건 미충족이면 어떤 메시지도 안 감 — "메시지가 없다 = 정상"
  이라는 전제가 필요한데, 이게 2절의 한계와 직결된다.

**실제 발생한 혼동 사례**: 이 문서 작성 세션에서 알림 발송 로직을 실기기로 검증하려고
phone #1 배터리를 60→58로 인위적으로 낮춰(`_battery_info`만 패치, `_send_telegram`은
실제 호출) 2회 연속 하락을 재현하는 테스트를 했고, 이때 실제로
`"현재 배터리 58% (직전 대비 -2%)"` 텔레그램 메시지가 진짜로 발송됐다(새벽 2시경).
이후 다른 세션에서 사용자가 아침 8시 29분에 이 메시지를 확인하고 "실제로 배터리가
줄고 있다"는 피드백을 줬는데, 확인해보니 같은 시간대의 `screen_watchdog.log`(cron이
실제로 남기는 로그)에는 "58%"나 "알림 전송함" 기록이 전혀 없어 — 즉 **테스트 때 보낸
메시지를 나중에 열람하면서 실제 알림으로 오인**한 것이었다. 테스트 메시지와 실제
알림 메시지가 형식상 구분이 안 되는 것도 원인 중 하나.

## 2. 지금 방식의 한계

프로토타입을 테스트하면서 나온 관찰:

- **정기 알림은 "이상 있는 기기만" 보고한다.** 배터리 하락 테스트 알림을 받아보니
  phone #2는 정상이라 아무 메시지도 안 왔다 — 이상 없음 자체가 안심 신호가 되어야 하는데,
  지금 구조로는 "알림이 없다 = 정상" 인지 "watchdog가 안 돌고 있다" 인지 구분이 안 된다.
- **on-demand 조회 수단이 없다.** 지금 당장 두 폰이 어떤 상태인지 궁금하면 노트북에서
  `adb shell dumpsys ...`를 직접 쳐야 한다. 외부에서(텔레그램으로) 즉시 확인할 방법이 없음.
- **정기 체크와 즉시 조회가 로직/데이터를 공유해야 한다.** 즉시 조회 시에도 "직전 체크 대비
  변화량"을 보여주려면 watchdog가 쌓아온 state(직전 레벨, 연속 카운트)를 그대로 읽어야
  자연스럽다 — 두 기능을 각자 따로 만들면 state가 두 벌로 쪼개진다.
- **테스트 알림과 실제 알림이 메시지 형식상 구분 불가** (1.6 사례). 실제 이관 시
  테스트/디버그 발송은 `[TEST]` 접두사 등으로 명확히 구분하거나, 아예 운영 모드에서는
  실제 발송을 막고 로그로만 확인하는 방식을 검토할 필요가 있다.

## 3. 제안하는 방향

### 3.1 신규 명령어: `/폰상태`

기존 `bot/handlers/screen.py`가 이미 phone #1 화면 제어(`/screen`)를 담당하고 있으므로,
같은 패턴(handler 모듈 + `ContextTypes` async 핸들러 + `_make_collector()` 스타일의
디바이스 접근 헬퍼)을 따라 신규 handler를 추가하는 것을 제안.

- 명령어: `/폰상태` (가칭 — `/screen`과의 네이밍 일관성 검토 필요)
- 대상: phone #1 + phone #2 둘 다 (기존 `/screen`은 phone #1 전용이었음 — 확장 필요)
- 표시 항목(1폰당):
  - 화면 on/off + lock 소유자(누가 쓰는 중인지, 있다면)
  - 배터리 %, 충전 여부, 직전 체크 대비 변화량(watchdog state 재사용)
- 예시 응답:
  ```
  📱 phone #1 (stockmonitor)
  🔅 꺼짐 · 잠금 없음
  🔋 34% (+6%) · 충전 중

  📱 phone #2 (stockmonitor_ji)
  🔆 켜짐 · stockmonitor 작업 중
  🔋 100% (+0%) · 완충
  ```

### 3.2 정기 감시 로직 이관

`~/screen_watchdog.py`의 판정 로직(화면+lock 조건, 배터리 하락 조건, 2회/20분 임계치,
one-shot 알림)을 honeybot의 기존 `bot/scheduler.py`(이미 정기 작업을 돌리는 인프라가
있음)로 이식. 장점:

- state 파일이 하나로 합쳐짐 → `/폰상태` 명령어와 정기 감시가 같은 state를 참조 가능
- 별도 cron 등록 없이 honeybot 프로세스 안에서 스케줄링 (honeybot이 이미 상시 구동 중)
- 텔레그램 발송 인프라(토큰, chat_id, 전송 함수)를 honeybot 것 그대로 재사용 —
  현재 프로토타입처럼 하드코딩 중복 없이 `config.py`를 통해 관리

### 3.3 데이터 모델

현재 프로토타입 state 스키마(기기 시리얼별):
```json
{
  "R3CR8051NNJ": {
    "screen_count": 0,
    "battery_count": 0,
    "alerted": false,
    "prev_level": 34
  }
}
```
이관 시 honeycard.db(sqlite, 이미 존재) 테이블로 옮길지, 지금처럼 JSON 파일로 둘지는
honeybot 세션에서 기존 상태 관리 컨벤션(예: `state_repo` 패턴이 `screen.py`에 이미
보임)에 맞춰 결정.

## 4. 스코프 밖 (이번 설계에서 다루지 않음)

- phone #1 배터리 리포팅 자체가 불안정한 문제(짧은 시간 내 34%→100%, status 2↔5 요동)는
  watchdog/명령어 설계와 별개 이슈. 기기/드라이버 쪽 원인 조사가 필요하면 별도 항목.
- `run_xwiki.sh` 수정 건은 이미 완료되어 스코프 밖.
